# AI Job Agent 技术决策记录

## 岗位JD分析输出格式

- 问题：大模型自由文本不稳定，无法可靠参与岗位匹配计算。
- 选择：使用Pydantic `JobRequirementResult`约束Structured Output。
- 备选方案：直接返回自然语言或手动解析普通JSON。
- 为什么选择：字段稳定、自动验证、便于前端展示和后续评分。
- 缺点：修改输出字段时，需要同步调整后端Schema和前端显示。
- 未来升级：增加Timeout、Retry、Token成本记录和Redis缓存。

## AI测试模式

- 问题：开发期间重复调用真实模型会产生费用，并受网络波动影响。
- 选择：通过`LLM_MOCK_MODE`在模拟结果和真实模型之间切换。
- 备选方案：每次都调用真实模型。
- 为什么选择：测试速度快、结果稳定、不会产生Token费用。
- 缺点：模拟结果不能证明真实模型效果。
- 未来升级：上线前关闭Mock，并建立真实岗位评测集。

## 多来源技能如何计分

- 问题：数据库技能和AI提取的必备技能可能重复，分别加分会让总分虚高。
- 选择：先将两个来源统一小写、去空格并去重，再作为一个35分技能维度计算。
- 备选方案：两个来源分别计分，或只采用AI结果。
- 为什么选择：保留人工数据与AI补充能力，同时避免同一技能重复计分。
- 缺点：AI误提取的技能可能扩大分母，需要通过岗位测试集继续校准。
- 未来升级：加入技能别名表和评测数据，记录调整前后的匹配结果。

## 职责匹配使用什么简历数据

- 问题：原简历分析只有总结和技能，没有可供职责匹配的结构化工作经历。
- 选择：新增 `work_experience` JSON列表，并通过数据库迁移保留已有记录。
- 备选方案：直接拿总结文本评分，或每次重新解析整份PDF。
- 为什么选择：经历数据可验证、可保存、可重复使用，也更容易展示匹配证据。
- 缺点：旧分析记录的经历默认是空列表，需要重新分析简历才能得到真实内容。
- 未来升级：增加项目经历和教育字段，并使用正式迁移工具管理MySQL结构。

## 第一版职责匹配为什么先使用关键词规则

- 问题：需要把岗位职责和简历经历进行匹配，并向用户展示可以核对的证据。
- 选择：第一版使用共享关键词寻找简历证据，按命中职责比例计算最高30分。
- 备选方案：直接让大模型给分，或立即引入Embedding语义匹配。
- 为什么选择：规则透明、成本为零、结果稳定、容易自动化测试，适合作为后续语义匹配的基线。
- 缺点：无法识别不同措辞表达的相同含义；过宽关键词可能产生误匹配。
- 约束：不把“开发”等通用词加入关键词表，避免为了提高分数制造虚假匹配。
- 未来升级：建立真实职责/经历测试集，再增加Embedding语义分并与规则分组合。

## 岗位方向为什么单独计分

- 问题：技能相似不等于岗位方向一致，例如会Python的人不一定想应聘所有Python相关岗位。
- 选择：把岗位名称与AI推荐岗位方向进行规则比对，方向一致时获得10分，并返回匹配原因。
- 备选方案：只使用技能分，或让大模型直接判断岗位方向。
- 为什么选择：规则透明、没有模型费用、容易测试，并能向用户解释推荐原因。
- 缺点：当前关键词表较少，无法识别所有岗位别名。
- 未来升级：根据真实岗位测试集补充岗位别名，并加入Embedding语义匹配。

## 求职偏好如何计入规则分

- 问题：技能和经历相符的岗位，仍可能因为城市或薪资不合适而不值得推荐。
- 选择：城市最高5分、薪资最高10分；岗位最高薪资达到用户最低要求时判定薪资符合。
- 备选方案：偏好作为硬过滤条件，或交给大模型判断。
- 为什么选择：第一版保留所有岗位供用户比较，同时用分数清楚表达偏好差异，规则无需模型成本。
- 缺点：当前只解析常见的`15-20K`格式，“面议”、日薪和年薪需要额外规则。
- 未来升级：建立真实薪资格式测试集，并根据用户反馈决定哪些条件改为硬过滤。

## 为什么在Embedding之前建立固定评测集

- 问题：加入语义匹配后，分数变化不代表推荐质量一定提高，甚至可能破坏已有正确排名。
- 选择：先固定一份模拟用户和3个代表岗位，记录规则基线分数与人工期望排名。
- 备选方案：只凭页面观感判断，或上线后再收集反馈。
- 为什么选择：结果可重复、修改前后可比较、可以进入自动化回归测试，也能形成面试证据。
- 缺点：当前只有3个案例，无法代表真实招聘市场的全部情况。
- 未来升级：从脱敏真实岗位中逐步增加正确、错误和边界案例，并记录准确率和排序指标。

## 第一版中文语义匹配使用什么模型

- 问题：关键词规则无法识别“开发FastAPI接口”和“构建Python REST API”这类措辞不同但含义接近的文本。
- 选择：使用本地`BAAI/bge-small-zh-v1.5`，通过Sentence Transformers生成归一化向量并计算相似度。
- 备选方案：调用外部Embedding API，或直接让LLM判断相似度。
- 为什么选择：中文效果适合当前场景、模型较小、可在CPU运行、结果可重复，并且开发测试不产生Token费用。
- 缺点：首次加载约十几秒并占用本机内存；相似度不是百分制，也不能未经评测直接设置固定合格线。
- 当前约束：语义结果先作为参考值返回，不直接加入现有100分规则总分，避免重复计分和未经校准的权重。
- 未来升级：扩充脱敏真实岗位评测集，比较加入语义层前后的排名，再决定阈值、权重和是否使用向量数据库。
